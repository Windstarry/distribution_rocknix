A311D 20261112  GAMES(P3) 最小恢复执行报告
==================================================

设备     192.168.31.7  AURKNIX 20261112  Linux 6.18.49  BUILD 85765b5c6d
操作对象 /dev/sda3（P3，LBA 19531776 起，46004224 扇区 / 23.55GB）
本次性质 按批准的「最小恢复」方案执行写操作 + 脚本加固
结论级别 已实测（设备端 + 介质层），非推断

---------------------------------------------------------------
一、执行摘要
---------------------------------------------------------------
1. 按方案执行 mkfs.exfat -n GAMES /dev/sda3 → sync → blockdev
   --flushbufs → 丢页缓存 → O_DIRECT 回读 VBR 校验。
2. mkfs.exfat 返回 0，输出 "exFAT format complete!"，但 VBR
   （分区第 0 扇区）回读为全 0xFF，校验不通过。
3. 追加受控写入实验（P3 内 12 个 LBA，分区为空、无用户数据）：
   全部写入返回成功，全部读回旧值或 0xFF。
4. 重启设备后复测：此前「看似存在」的 P3 位图（sec 8192）与根目录
   （sec 8448，含 GAMES 卷标项）也变成全 0xFF。
5. 判定：该 U 盘在 P3 所在 LBA 区间不落盘，写入被静默丢弃。
   不是脚本问题、不是分区表问题、不是 mkfs 工具问题、不是内核问题。
   换任何脚本或镜像都无法在本盘 P3 建立可挂载文件系统。
6. 因此「最小恢复」在本盘上不可能完成。正确处置是更换介质；
   脚本侧加固已按要求落地并通过实机正/负例验证。

  mkfs.exfat -n GAMES /dev/sda3

  sync → blockdev --flushbufs /dev/sda3（及 /dev/sda）→
  echo 3 > /proc/sys/vm/drop_caches
  dd if=/dev/sda3 bs=512 count=1 iflag=direct
    → ff ff ff ff ... （全 0xFF，无 eb7690 / "EXFAT" 魔数）
  blkid -p /dev/sda3
    → 仅 PART_ENTRY_*，无 TYPE
  备用 VBR（sec 12）→ 全 0xFF
  整盘偏移 19531776 直接读 → 全 0xFF（排除分区节点偏移错位）

[2.4] 受控写入实验（P3 内，数据可丢弃）
  写入 LBA（分区内扇区号）：0 12 2048 8192 8448 40000000
    → dd 全部 rc=0
  回读（O_DIRECT）：全部 ff，或仍是旧内容（8192 = 1f 00 00…）
  dirty/writeback 均为 0kB；写入后立即用普通（非 O_DIRECT）读
  仍返回 0xFF —— 说明数据连页缓存都没进，是被设备「收下即丢」。

[2.5] 边界扫描（分区内 0 / 16 / 1024 / 4096 / 8192 / 16384 /
      65536 / 262144 / 1048576 / 4194304 / 16777216 / 44000000）
    → 12 个点全部写入成功、全部读回 0xFF 或旧值，无一落盘。

[2.6] 分区表外空隙探测（排除「分区边界」与「LBA 边界」两种解释）
    → LBA 19531251 / 19531300 / 19531500 / 19531700 / 19531775 /
      19531776 / 19531800 / 19532288 全部写入后读回 0xFF
    → 连 10GB 以下的 LBA 19520000 / 19531000 / 19531240 也读回 0xFF
    → 失效边界与 P3 起点无关，位于更低 LBA（< 9.99GB）

[2.7] 对照实验（证明链路与文件系统层正常）
    /storage（P2 ext4）写 4MiB 文件 + fsync → drop_caches →
    md5 一致（b5cfa9d6c8febd618f91ac2843d50a1c）
    → 同样的 USB 链路、同样的内核，P2 区间写入正常持久。
    注意：文件级 seek 只改变文件偏移，ext4 块分配由分配器决定，
    不能用来证明对应物理 LBA 可写，故不作为高 LBA 可写的证据。

[2.8] 重启后复测（关键）
    reboot -f → 重新连上
    P3 sec 0 / 8192 / 8448 → 全部 0xFF
    说明上一轮「读到的 exFAT 位图与 GAMES 根目录」只存在于控制器
    缓存中，掉电即失，从未真正落到闪存。
    重启后重新写入 0 / 2048 / 8192 / 40000000 → 仍全部丢弃。

五、脚本变更清单
---------------------------------------------------------------
文件：projects/ROCKNIX/packages/sysutils/busybox/scripts/fs-resize
（+147 / -33）

1. 新增 partition_device()：mmcblk/nvme 用 pN，其余用 N，去掉原先
   两处重复的分支拼装。
2. 新增 flush_partition()：sync → blockdev --flushbufs → sync →
   drop_caches，保证后续校验读的是介质内容而不是内存。
3. 新增 games_fs_valid()：O_DIRECT 读取分区第 0 扇区偏移 3 的 8 字节，
   要求 "EXFAT" 魔数，并要求 blkid -p 报 TYPE="exfat"，两者同时成立
   才算有效。这是本次问题的直接检测手段。
4. 新增 ensure_games_partition()：
   - 先判有效则直接跳过（幂等，避免每次启动重格式化）；
   - 分区条目已存在则不再 mkpart，只做格式化；
   - mkpart 后补 partprobe + udevadm settle + sleep 1，消除重读竞态；
   - 捕获 mkfs.exfat 返回码，失败最多重试 2 次，每次重试后都回读校验。
5. 失败不再删除标记（这是原设计的致命点）：
   - 写 /flash/.games_pending 记录目标尺寸；
   - 重新 touch /storage/.please_resize_me —— init 第 1420 行只在
     /sysroot/storage/.please_resize_me 存在时才启动 fs-resize.target，
     删掉它等于永久放弃自愈；
   - 下次启动走「仅重试格式化」分支，不再重复 parted/resize2fs。
6. 重试上限 3 次（/flash/.games_retry），达到上限只记录并跳过本次启动，
   避免坏介质上每次开机都长时间格式化；标记保留，人工可重置。
7. 只有校验通过才删除 resize_storage_* / .games_pending /
   .games_retry / .please_resize_me。

八、建议下一步
---------------------------------------------------------------
1. 换盘（必须）：
   选正品 U 盘，32GB 以上、U3/A1、金属壳散热好。
   到手先在 PC 上用 h2testw（或 f3write/f3read）做全容量写校验，
   通过后再刷镜像。这一步能提前筛掉扩容盘和坏块盘。
2. 刷写后核对：
   blkid /dev/sdX3 应显示 TYPE="exfat" LABEL="GAMES"
   parted -s -m /dev/sdX print 第 3 分区起点应与 resize_storage_10G 一致
   /storage/games-external 应已挂载且可写
3. 重新构建：本次脚本改动需重建 SYSTEM 才会进入镜像；重建后建议同时
   确认 fs-resize.log 中出现 "GAMES: ... formatted and verified"。
4. 不建议继续使用当前这块盘：即使把布局压小绕开失效区，该盘已证明会
   静默丢写，/storage 上的数据同样不可信。
