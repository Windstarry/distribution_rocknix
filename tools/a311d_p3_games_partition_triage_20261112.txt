AURKNIX A311D —— GAMES(P3) 分区无文件系统 只读定位报告
生成时间：2026-11-12 19:4x（北京时间）
排查对象：设备 192.168.31.7（AURKNIX，6.18.49，OS 20261112，BUILD_ID 85765b5c6d）
          电脑端 U 盘：Kingston DataTraveler 3.2 64GB，当前盘符 G: / H:
排查方式：SSH 只读 + 本机镜像/盘符只读解析（O_DIRECT 复核）
本次未执行：任何写分区、格式化、刷写、reboot 操作

====================================================================
一、结论（先看这一节）
====================================================================
1) 分区表本身没有问题。P3 的起始扇区、长度、类型全部正确：
   起始 LBA 19531776（10,000,269,312 B），长度 46004224 扇区（23.55 GB / 21.94 GiB），
   MBR 类型 0x07。0x07 不是"NTFS 文件系统"，它只是 exFAT 在 MBR 下的惯用类型字节，
   这与我们在 3f062a4b1e 里修正过的行为一致。

2) 真正缺的是 P3 的 exFAT 卷头（VBR）和 FAT 表：
   P3 的 0 ~ 7679 扇区（主引导记录区 0~23、FAT 区 2048~7679）全部是 0xFF；
   而从 8192 扇区（簇堆起点）开始，mkfs.exfat 的产物完整存在：
     - 8192 扇区：分配位图首字节 1f 00 00 00（簇 2~6 已占用，空卷特征）
     - 8448 扇区：根目录项 83 05 "G A M E S"（卷标项）+ 81（位图项）+ 82（大写表项）
   也就是说：格式化确实执行了，但只落地了后半段，卷头没有落地。

3) 因为没有 VBR，任何系统都只能判定"无文件系统"：
   Linux blkid 只输出 PART_ENTRY_*，没有 TYPE；/storage/games-external 为空，
   GAMES 不挂载；Windows 侧显示未格式化/无盘符。这与"分区被删"是两回事。

4) 之所以永久无法自愈，是脚本的健壮性缺陷：mkfs.exfat 的返回码没有检查、没有回读校验，
   失败后仍然删除了 /flash/resize_storage_10G 与 /storage/.please_resize_me，
   而后续启动又会被 "the system has already been initialised" 拦住，永远不会再补格式化。

  两个盘符：G:（P1，卷标 ROCKNIX，FAT32 2GiB）、H:（P3，卷标 GAMES，exFAT 49.28GiB）。

四、问题定位（精确到扇区）
====================================================================
分区容器：OK（P3 起点/长度/0x07 类型/内核视图一致，无重叠、无越界）
文件系统：半成品
  - 缺失：P3 扇区 0（主 VBR）、12（备份 VBR）、2048~7679（FAT）
  - 存在：8192 起的簇堆（位图、大写表、根目录卷标）
判定：exFAT 卷不可枚举 → blkid 无 TYPE → 不自动挂载 → Windows 报未格式化

====================================================================
五、根因分析（分层，按证据强弱）
====================================================================
【直接原因】mkfs.exfat 的卷头与 FAT 写入没有落到介质上。

【机制候选，按可能性排序】
A. U 盘写缓存/FTL 未把卷头写入提交（最可能）
   内核对该盘 "Assuming drive cache: write through"，不会下发 SYNCHRONIZE CACHE；
   脚本在 mkfs 之后只有一条 sync，接着 5 秒倒计时就 reboot -f 硬复位，
   没有 blockdev --flushbufs、没有 unmount/eject、没有回读校验。
   控制器（CBM2199 类桥接）把最前面的元数据留在自身缓存，复位掉电即丢。
   已落盘的簇堆（后写）与丢失的卷头（先写）在时间上相邻，符合"缓存只丢一部分"的表现。

B. 该盘（VendorCo ProductCode / 64GB 变体以外的 32GB 廉价盘）在高 LBA 区写入不可靠
   但这块盘 11-09 曾在该偏移成功格式化，且 P2 ext4 在 6.58 GB 处的备份超级块完好
   （s_blocks_count=0x001d30be=1913022，与 resize2fs 结果一致），
   说明高 LBA 写入总体是能落盘的，此假设只能解释"局部扇区"而非整段 3.75 MB。
   若要坐实，必须做"写入+回读校验"的受控测试（本轮不允许写）。

C. 分区表重读竞态（mkfs 时 /dev/sda3 还是旧节点）
   本轮证据不支持：偏移一致、heap 落点与 heap_offset=8192 完全吻合、日志无 "No such file"。
   但脚本确实缺少 partprobe/udevadm settle，属于应当补上的防御。

【放大因素（脚本缺陷，无论 A/B/C 哪个成立都必须修）】
1. mkfs.exfat 的返回码被 StartProgress 丢弃，失败也继续往下走并打印
   "Created new GAMES partition on /dev/sda3"。
2. 没有格式化后的回读校验（读 VBR 前 11 字节是否为 eb 76 90 "EXFAT   "，
   或 blkid -p 是否识别 TYPE=exfat）。
3. 失败后仍然 rm -f /flash/resize_storage_*，并已删除 /storage/.please_resize_me，
   而下一轮启动会被 "Resizing is not permitted - the system has already been
   initialised." 直接拦住 → 一次失败永久固化，不可能自愈。
4. 缺少 partprobe / udevadm settle、blockdev --flushbufs、双 sync、eject/延迟断电。
5. 先扩 P2 到 10G 再 mkfs；mkfs 失败时空间已被占用，用户只剩一个 23.6G 的空壳分区。

七、修复建议（按优先级）
====================================================================
P0 脚本硬化（projects/ROCKNIX/packages/sysutils/busybox/scripts/fs-resize）
  a. 捕获 mkfs.exfat 返回码：失败则不删标记、不打印成功、保留 resize_storage_10G 供下次重试。
  b. mkfs 后 partprobe "$DISK" + udevadm settle，确认 $GAME_PART 节点存在且 size 正确。
  c. 写入回读校验：dd 读 $GAME_PART 前 512 B，校验 00:03 == eb 76 90 且 03:11 == "EXFAT   "，
     并用 blkid -p 校验 TYPE=exfat；任一项失败视为失败。
  d. 落盘：sync; sync; blockdev --flushbufs "$DISK"; 再 sleep/倒计时后 reboot，
     或改为正常 reboot（非 -f），给 USB 桥接器 flush 的机会。
  e. 失败回退：mkfs 失败时删除 P3 并把 P2 扩回 100%，避免"7.3G 存储 + 23.6G 空壳"的死局。
  f. 自愈：若 /flash/resize_storage_* 存在且 P3 无有效 exFAT，允许在已初始化系统上
     仅做"补格式化"（不重新分区），需要显式开关，避免误扩。

P1 现场恢复（需要写操作，本轮未执行，需你确认）
  - 方案 1（推荐，最小改动）：在设备上执行 mkfs.exfat -n GAMES /dev/sda3，
    随后 sync + blockdev --flushbufs，再回读校验 VBR，最后 reboot 验证自动挂载。
  - 方案 2：把盘接回电脑，用 Windows 格式化该分区为 exFAT（会丢 MBR 类型一致性优势，
    但可用），或直接用 DG 重新格式化。

P2 流程与闸门
  - PC 端刷盘流程规范化：刷完不做整盘 clean，只覆盖镜像长度内的扇区。
  - CI 增加静态闸门：fs-resize 必须包含 mkfs 返回码判断与 VBR 回读校验。
  - 留档：把本次"半成品格式化"的扇区分布加入 tools/a311d_games_partition_check.py
    的判定规则（VBR 缺失但簇堆存在 → 明确输出"格式化未落盘"，而不是笼统的"无文件系统"）。
