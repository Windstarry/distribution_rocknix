【1.1 影响范围】

【1.3 可能的根因（事实 / 推断分开）】
  已确认事实：
    F1 实机 MBR 类型 P1=0x0c、P2=0x83、P3=0x07、P4=0x00；
       P3 分区条目与 2026-11-09 记录完全同边界（start 19531776 / size 46004224），
       但前 64 字节全 0xFF；11-09 的 games_partition_check_20261109.json 记录当时
       P3 有有效 exFAT BPB（eb7690 / EXFAT / 23,554,162,688 B）。
       => P3 分区条目被保留，文件系统被清空或重建后未完成格式化。
    F2 本次启动没有执行任何设备端分区脚本：/flash/fs-resize.log 未被写入（mtime
       2024-06-25）、/storage/.please_resize_me 不存在、journalctl 无相关痕迹。
       => 当前三分区布局与 P3 的 0xFF 状态，是上电前（PC 刷写/分区阶段）形成的。
    F3 HW_DEVICE=A311D，installtointernal 的白名单会在第 16 行 exit 1；
       /dev/mmcblk0 不存在，Install AURKNIX to EMMC.sh 会在第 117 行 exit 1。
       => 本次启动这两个脚本都不可能执行。
    F4 镜像内唯一「安装后自动执行」的分区脚本是 fs-resize，其代码只做
       resizepart 2 与 mkpart 3，没有 mklabel / rm 全部分区的能力。

  推断（按可能性排序，均需下一步取证确认）：
    R1【最可能】PC 端刷盘/分区流程重建了 MBR。用户在「安装完成」后用 DiskGenius
       或自建分区脚本处理 U 盘（刷机说明.txt 明确记录 DG 克隆前两分区）。
       若执行了「删除全部分区 / diskpart clean / 重新建立 MBR」再按原边界重建，
       P1/P2 内容由镜像克隆恢复、P3 只建了条目未格式化 -> 与 F1 完全吻合；
       若重建时 P1/P2 未恢复或卷标丢失 -> 重启即 "Unable to find LABEL=ROCKNIX"。
    R2 用户曾手工触发安装类脚本，且当时条件与本次不同（例如 HW_DEVICE 被改写、
       插入了第二块 USB 导致 sda/sdb 漂移、或目标 mmcblk0 存在）。
       installtointernal 的 DEVICE=/dev/sda 与 EMMC 脚本的 seek=462 count=48
       都具备「删除/重建全部分区表」的破坏力，且都没有启动盘排除校验。
    R3 fs-resize 在异常条件下误判目标盘或重复执行（可能性较低，代码不删全部分区），
       但存在两个真实隐患：TARGET_SIZE=100% 会把 P2 扩到盘尾，与既有 P3 冲突；
       mkfs.exfat 失败不会回滚，日志又预置了「exFAT format complete!」的成功文本，
       极易误导排查，让人以为 GAMES 分区已格式化。

  共同的设计缺陷（无论 R1/R2/R3 哪个成立都必须修）：
    所有安装/扩容脚本的目标盘都是硬编码或弱判定，
    没有「当前启动盘 = /proc/mounts 中 /flash、/storage 所在磁盘」的强制排除；
    也没有 HW_DEVICE、介质类型、容量、可移动属性的交叉校验。
    A311D 从 USB 启动时 /dev/sda 恰好就是系统盘，硬编码的风险被放大。

【1.4 建议处理方向（本次不实施）】
  1. 先固化基线：只读导出 MBR 512B、parted -s -m print、blkid、三分区镜像与 sha256，
     连同 /flash 全部文件备份；保留 G 盘可回退系统。任何改动前完成。
  2. 给所有涉及磁盘写操作的脚本加统一守卫函数：
     从 /proc/mounts 取 /flash 与 /storage 的父磁盘 BOOT_DISK，
     若 TARGET == BOOT_DISK 立即 abort 并打印明确错误；
     同时校验 HW_DEVICE 白名单、目标盘为块设备、容量下限、盘序号唯一性。
  3. 删除硬编码：installtointernal 的 DEVICE=/dev/sda 改为运行时探测 + 白名单；
     EMMC 脚本的 mmcblk1/mmcblk0 改为按 dtname / 介质类型判定，并禁止对可移动 USB 盘操作；
     installer 的 get_device_unmount() 由字符串 sed 改为精确列表过滤。
  4. fs-resize 增加幂等与 dry-run：检测已有第三分区时跳过 mkpart；
     resizepart 前校验 P2 结束位置 < P3 起始位置；
     mkfs.exfat 后回读 BPB 校验并把结果写入本次日志（禁止沿用镜像内预置成功日志）；
     失败时保留分区表不回滚到破坏性状态。
  5. PC 端流程约束：先整盘写入镜像（含 MBR），再按镜像分区表校验；
     禁止 clean/删除全部分区；需要 GAMES 分区时只做增量 mkpart + mkfs.exfat；
     每次操作前后各存一份 MBR 分区表快照。
  6. CI 闸门补静态检查：脚本中出现 mklabel /dd of=\/dev\//parted -s .* rm
     时，必须同时存在 BOOT_DISK 排除守卫，否则构建失败。

  ⚠ parted rm / mklabel / dd of=/dev/sdX 不可逆，会同时丢失 P1 引导文件、
    P2 用户配置与存档、P3 游戏数据；执行前必须整盘备份并逐项确认。

    R3 值映射不一致：UI 若写入 zh-CN / Chinese / zh 等而非 zh_CN，
       get_setting 取不到有效值，localedef -i <值> 也会失败并静默回退。
    R4 字体链路独立：系统字体目录无 CJK 字体，仅 ES resources 内有
       DroidSansFallbackFull.ttf。若主题 zh.xml 未指定或 ES 未选用该字体，
       中文会渲染成方框/空白，用户可能误判为「切换无效」。

【2.4 建议处理方向（本次不实施）】
  1. 先做写入链路取证：在 UI 选中文前后 diff
     /storage/.config/system/configs/system.cfg 与 es_settings.cfg，
     抓 journalctl -u essway.service 与 ES 日志，确认「到底写没写、写成了什么值」。
  2. 分两种情况修：
     未写回 -> 修 ES 设置持久化路径/键名/权限（/storage 为 rw，应可写），
               并明确 UI 切换后是否需要提示重启 ES 或整机；
     已写回 zh_CN 但仍英文 -> 查 /var/log/start_es.log、localedef 返回码、
               LC_NAME 是否生成、LANG 是否经 systemctl import-environment 生效。
  3. 强化 es_settings：localedef 失败要显式记录并回退到 en_US（而不是静默），
     生成前校验 .mo 路径 <LOCPATH>/zh_CN/LC_MESSAGES/emulationstation2.mo，
     生成后校验 LC_NAME；把日志改为追加且保留返回码。
  4. 默认值策略：谨慎处理 system.language=en_US 全局默认。
     若要求开机即中文，建议做成设备/区域可配置项或首次启动向导，
     不要直接全局改（会影响所有设备与所有语言用户），并定义 /storage 配置的迁移策略。
  5. 字体链路：确认 zh.xml 或 ES 默认字体映射到 DroidSansFallbackFull.ttf；
     必要时向 /usr/share/fonts 补 CJK 字体并做渲染验证。
  6. 加只读自检（可并入 CI 或 tools/）：检查 system.language 值、ES 进程 LANG、
     locale -a、LC_NAME、.mo 存在性、CJK 字体，输出 PASS/FAIL，避免只靠肉眼判断。

【2.5 验证要点】
  - UI 选中文并重启 ES 后：get_setting system.language = zh_CN；
    /proc/<es_pid>/environ 中 LANG=zh_CN.UTF-8、LANGUAGE=zh_CN.UTF-8；
    LOCPATH 指向含 zh_CN/LC_MESSAGES 的目录。
  - locale -a 含 zh_CN.UTF-8；zh_CN.UTF-8/LC_NAME 非空；
    /var/log/start_es.log 无 localedef 错误且有明确成功/失败状态。
  - ES 界面菜单出现中文且字形正常（非方框）；主题 zh.xml 生效。
  - 反向验证：切回 en_US 能恢复英文，证明是切换链路而非硬编码英文。
  - 持久化验证：冷启动两次后仍保持中文，确认 /storage 配置未被覆盖。
  - 附带验证：切换语言不影响 sway/essway active、不影响 /dev/dri 与 panfrost。

【2.6 风险提示】
  ⚠ system.cfg 位于 /storage（用户数据区），OTA/重刷后可能被保留或覆盖，
    默认值改动需明确兼容与迁移方式，否则会出现「改了镜像但设备仍是 en_US」。
  ⚠ es_settings 与 ES 本体在只读 squashfs 内，不能活机直接改，
    必须完整重建 SYSTEM 并重新刷盘；本次禁止在活机上修改任何文件。
  ⚠ localedef 在嵌入式 CPU 上耗时明显（脚本内专门调用 performance 提频），
    首次切换可能卡顿；必须有失败回退，否则可能拖慢甚至阻塞 ES 启动。
  ⚠ 语言与字体是两条独立链路，只修语言不修字体仍可能「看起来没变」。
  ⚠ UI 切换可能需要重启 ES/整机才生效，需向使用者说明，避免误判为无效。
  ⚠ 该问题不影响启动与数据安全，可延后；但因其需重建 SYSTEM，
    建议与问题一的修复合并为同一次重建，减少刷盘次数与回归成本。
