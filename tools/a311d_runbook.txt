二、启动过程
--------------------------------------------------------------------------------
2.1 上电前 LAN 基线 (必须做, 否则判定不可信)
  命令: python a311d_bringup_probe.py --once --save-baseline \
          E:\A311d\AURKNIX-image-A311D-20261031\baseline_F_20261109.json
  通过: 生成基线文件, 记录上电前已存在的 22/445/5555/80 主机
  失败: 无文件 -> 检查 --subnet 是否为盒子网段 (默认 192.168.31)
  依据: 本网段实测存在其他 SSH/Samba 主机 (192.168.31.3:22/445,
        192.168.31.55:445, 192.168.31.1:80), "见 22 就算成功"会误判
  本次实测 (2026-11-09 20:31, 盒子上电前): 已生成 baseline_F_20261109.json
        既有开放端口 = 192.168.31.1:80 / 192.168.31.3:22,80,445 /
        192.168.31.55:445; 5555 无 (安卓未在线); 192.168.31.7 仅 ARP 残留,
        无开放端口 -> 判定盒子当前未启动, 可作基线

2.2 上电时序
  操作: U 盘插 EE 能启动的那个 USB 口 -> 接网线 -> 接 HDMI -> 上电;
        保持供电 3~5 分钟 (首启扩容会自动重启一次, 期间严禁断电)
  通过: 2.3 观测到明确的 BOOTING -> BOOTED 稳定状态
  失败: 5 分钟纯黑屏且设备完全无端口响应 -> 5.1

2.3 网络时间轴观测 (启动阶段的首选手段)
  命令: python a311d_bringup_probe.py --watch --device-ip 192.168.31.7 \
        --baseline E:\A311d\tools\baseline.json --duration 300 --interval 10 \
        --out E:\A311d\tools\bringup_log.jsonl
  判定: BOOTED             = 设备 22 在线且相对基线是新增主机
        BOOTING            = 设备 445/139 在线但 22 未就绪 (服务还在拉起)
        REBOOTING          = 设备上一轮在线、本轮全静默 (fs-resize reboot -f)
        ANDROID_FALLBACK   = 设备 5555 在线 -> 5.3
        NO_LINK            = 设备持续全静默 -> 5.1
        BOOTED_UNCONFIRMED = 未给基线, 需补 2.1 后重判
  通过: 连续 3 轮以上 BOOTED 且 22/445 不再抖动, JSONL 有时间戳记录
  失败: 5 分钟后仍在 BOOTING/REBOOTING 循环 -> 5.4 或 5.7
  本次实测 (60 s, 端口 22/445/5555/80):
        t+4s  192.168.31.7:22/445
        t+19s 192.168.31.7:22/445
        t+33s 192.168.31.7:22        (445 暂退)
        t+48s 192.168.31.7:445       (22 暂退)
        t+63s 192.168.31.7:22/445    (恢复)
        => 典型启动阶段/服务重启特征, 不是内核已死

2.4 首启扩容
  观察: 出现 "Resizing storage partition..." -> 自动重启 -> 网络重新出现
  通过: 重启后设备 22 稳定在线, 且 3.3 里 /storage 容量 > 32 MiB
  失败: 扩容中断电/反复重启 -> 5.4

        ① 确认已过 2.4 的扩容重启, 系统进入最终 rootfs
           (启动阶段的 22 可能由 initramfs/临时 SSH 提供, 凭据与最终系统不同)
        ② firstboot 写 ssh.enabled=0 与 rotate.root.password=0, 最终系统可能
           需要在设置界面开启 SSH; 22 在线但认证失败不等于系统没起来
        ③ 若仍不通, 用串口 (ttyAML0,115200n8, 可选硬件) 或本地终端确认
  本次状态: 未完成。用户确认当前仍在启动阶段、默认口令不通过;

3.2 挂载与卷标一致性 (最高优先级待确认项)
  命令(设备上): cat /proc/cmdline; findmnt /flash; mount | grep -E "flash|storage"; lsblk -f
  通过: cmdline 含 boot=LABEL=ROCKNIX disk=LABEL=STORAGE; /flash 已挂载且有 SYSTEM;
        /storage 位于 P2 且容量已扩; 无 "can't find LABEL" 类 dmesg
  失败: /flash 未挂载 -> 5.5 (AURKNIX rootfs 可能仍按 LABEL=AURKNIX 找 flash)

3.3 扩容结果
  命令: df -h /storage; lsblk; cat /flash/fs-resize.log 2>/dev/null;
        ls -l /storage/.please_resize_me
  通过: /storage 容量接近 U 盘剩余空间 (默认) 或 10 GiB 且存在 GAMES 分区;
        .please_resize_me 已消失; fs-resize.log 无 error
  失败: 仍为 32 MiB -> fs-resize 未执行 (/flash 不可写或触发文件丢失) -> 5.4

3.4 引导链一致性
  命令: md5sum /flash/kernel.img /flash/dtb.img; cat /flash/SYSTEM.MD5
  通过: 与 1.1 报告中的镜像内 md5 一致; /flash 下无 cfgload_env / device_trees
  失败: 不一致 -> U 盘被改写或刷错镜像, 回到 1.2

五、异常情况 (判定 + 处置 + 成功标准)
--------------------------------------------------------------------------------
5.1 纯黑屏 + NO_LINK (设备无任何端口)
  判定: FAIL, 内核早期挂 / PHY 未起 / U-Boot 未执行 aml_autoscript
  处置: ① 换 EE 能启动的 USB 口 ② 复核 Rufus DD 模式与 1.3 报告
        ③ 有条件时接 UART (ttyAML0,115200n8, 可选硬件) 抓 "Starting kernel" 之后的日志
  成功: 串口出现内核解压/启动日志, 且随后 22 在线

5.2 黑屏但 22 稳定在线
  判定: 部分 FAIL (系统已起, 显示未初始化)
  处置: SSH 查 dmesg | grep -iE "hdmi|drm|meson"; cmdline 已固定
        video=HDMI-A-1:1920x1080@60, 换显示器/线/口; 检查 /flash/cfgload 的 bootargs
  成功: HDMI-A-1 connected 且输出画面

5.3 ANDROID_FALLBACK (5555 开, 22 关)
  判定: FAIL, U 盘引导链未被 stock U-Boot 采纳
  处置: 换 USB 口 -> 重刷 (DD 模式) -> 用 E:\tools\YesStbTool-7D0\adb.exe
        connect <ip>:5555 确认安卓身份 -> 必要时试 SD 卡槽
  成功: 22 出现且 5555 消失

5.4 扩容中断电 / 反复重启 (BOOTING-REBOOTING 循环超过 5 分钟)
  判定: FAIL (数据风险), 不要手动改分区
  处置: 重新刷盘 (1.2 -> 1.3), 确认 P2 仍在, 保持供电 5 分钟;
        有条件时串口观察 fs-resize 的 parted/e2fsck/resize2fs 输出
  成功: 重启后 /storage > 32 MiB 且系统稳定

5.5 /flash 未挂载或卷标不匹配
  判定: FAIL (影响升级、config、扩容日志)
  处置: 不要单独改 FAT 卷标! 必须同步改三处: BPB volume label、
        kernel.img Android header 的 cmdline、cfgload 的 bootargs;
        只改一处会让 boot=LABEL 找不到 SYSTEM 而直接黑屏
  成功: findmnt /flash 有输出且 /flash/SYSTEM 可读

5.6 换 DTB 后仍黑屏
  判定: 非 DTB 问题。已实证: EE 菜鸟 DTB + 未压缩 ramdisk 在 CI 镜像上仍黑屏,
        根因是 CI 镜像空 cmdline + 外部 zstd ramdisk
  处置: 回到 bootsafe 链, 不再单独替换 dtb.img; 需要新外设时整体合入新 DTB

5.7 仍在启动阶段 / 22 在线但口令不通过 (本次实际状态)
  判定: 未定 (不是 FAIL)。端口只证明网络层有服务, 不证明最终 rootfs 就绪
  处置: ① 保持供电, 不要反复试密码 (可能触发锁定/干扰首启)
        ② 用 2.3 的 --device-ip 命令观察, 等 BOOTING/REBOOTING -> 连续 BOOTED
        ③ 首启扩容会 reboot -f 一次, 22/445 抖动属正常
        ④ 稳定后再执行 3.1; firstboot 的 ssh.enabled=0 可能要求在系统设置里开启 SSH
        ⑤ 超过 5 分钟仍不稳定 -> 串口抓日志 (唯一权威手段)
  成功: 连续 3 轮 BOOTED + 3.1 登录成功 + 3.2 /flash 挂载正常
  失败: 5 分钟后仍无稳定 22 或始终认证失败且串口显示 rootfs 挂载失败 -> 回到 5.5

5.8 控制台出现 [FAILED] Failed to start rocknix-report-stats.service (本次实际状态)
  性质: 非致命。该服务是 Type=oneshot, 仅由 rocknix-report-stats.timer
        (OnBootSec=5min) 触发; 全仓库无其它 unit Requires/Wants/After 它,
        rocknix.target 只 Requires=multi-user.target + graphical.target
        -> 它失败不会中断升级流程, 也不会阻止进入 EmulationStation
  根因: ① 旧脚本用 ping -c 1 8.8.8.8 判定联网, CN 上行 ICMP 基本不通
        ② 端点 https://rocknix.dpdns.org (第三方 DDNS) 不可达
        ③ 5 x 60s 重试后 exit 1 -> systemd 标 failed, 系统变 degraded
        ④ post-update:303 每次升级都删除
           /storage/.cache/rocknix-stats-reported -> 每次升级必复现
  判定: 通过 = 能进主界面 / 22+445 稳定 / systemctl is-system-running
              最多为 degraded 且 --failed 只列出这一个单元
        失败 = 屏幕停在 "Performing post-update configuration..." 或

5.12 三分区已生成, 但第三分区被 Windows 报 "FAT32 / 损坏 / 未格式化"
     (2026-11-09 实机确认, 非扩容失败)
--------------------------------------------------------------------------------
现象     : 首启后出现 3 个分区, Windows 把第三分区显示成 FAT32 且提示
           "损坏, 未格式化"; 手动格式化为 exFAT 后盘符仍可能显示 RAW。
取证     : F:\fs-resize.log 明确记录 mkfs.exfat -n GAMES /dev/sda3
           "exFAT format complete!" -> 扩容脚本本身执行成功, 不是格式化失败。
           G: 首扇区 = EB 76 90 "EXFAT   ", BPB 完整:
             512 B/sector, 64 sectors/cluster, FatOffset 2048,
             ClusterHeapOffset 8192, RootDirCluster 6,
             VolumeLength 46,004,224 sectors (21.94 GiB)
           -> 文件系统数据层完全合法。
根因     : fs-resize 用 parted ... mkpart primary **fat32** 创建第三分区,
           在 MBR 写入 type 0x0c (FAT32 LBA); 随后却格式化为 exFAT。
           Windows 按 0x0c 交给 FAT32 驱动, 读 BPB offset 11 (exFAT 该处为
           全 0) 判为无效 -> 显示 "FAT32"(来自分区类型) + "未格式化"。
           exFAT 在 MBR 上应使用 type 0x07; Linux blkid 按内容探测不受影响,
           所以设备端一直能正常挂载, 问题只在 Windows 侧。
本次盘   : 用户手动格式化后 MBR type 已变为 0x07 (Get-Partition MbrType=7),
           exFAT boot sector 合法 -> 该盘无需重刷、无需再改分区。
           一键验收: python tools/a311d_games_partition_check.py
                       --volume G: --disk 2 --json games.json
                     (--disk 需管理员; 无权限时 TC-GP-04..06 记 SKIP)
           Windows 仍显示 Unknown/RAW 属于挂载管理器缓存, 安全弹出后重新
           插入即可; 也可在磁盘管理里做一次 "重新扫描磁盘"。
           手动格式化会清掉卷标 (exFAT 根目录无 0x83 项); ROCKNIX
           automount 按 blkid TYPE="exfat" 选择分区, 不依赖卷标,
           因此功能不受影响; 若要与 GAMES 命名一致可执行:
             cmd /c "label G:GAMES"
修复     : projects/ROCKNIX/packages/sysutils/busybox/scripts/fs-resize
           把 mkpart primary fat32 改成 mkpart primary ntfs (仅借 0x07 类型
           标签, 不会创建 NTFS), 并在格式化后追加 parted print 便于取证。
