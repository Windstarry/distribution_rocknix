一、结论摘要
--------------------------------------------------------------------------------
1. 实验 A 已完成，结果为诊断报告第四节的判读 A2。[实证-板级]
   固定 F 盘（048d:1234 / CBM2199 / 32 GB）不变，仅把 G 盘已验证的
   6.18.49 kernel.img 换到 F 盘，上电后不再出现
   "Unable to find LABEL=ROCKNIX ... Power off in 3s"，开始进入
   系统初始化界面。

2. 「启动盘」与「内核版本」两个长期共线的变量至此已被分离。[实证-字节
   + 实证-板级] 同一块 CBM2199 盘、同一套 U-Boot 脚本、同一个 dtb.img、
   同一个 cmdline、同一个卷标、同一个 SYSTEM，只换 kernel.img 就从
   「找不到块设备」变成「进入系统初始化」。因此：

     [已排除] CBM2199 盘侧硬件/主控不兼容（盘 A1 判读的反面）
              盘在 6.18.49 kernel.img 下可完成 USB 存储绑定并挂载 /flash。
     [已排除] 阶段 B 六特征引导链（cmdline / ramdisk_size=0 / 三件套 /
              54,984 B dtb.img / 卷标 ROCKNIX / 无 ceboot）配置有误。
              六特征在本轮实机中被同一块盘、同一套字节验证通过。
     [已排除] 刷盘不完整、md5 不符、附加文件缺失。
     [已收敛] 故障唯一变更项 = 20261111 的 6.18.21 kernel.img 内容
              （内核本体 + 内建 initramfs 二者作为一个整体）。

3. 口径限定（不得越级）：
   [可以写] 「引导失败已收敛到 6.18.21 kernel.img 与 6.18.49 的行为差异」。
   [不得写] 「6.18.21 内核驱动缺 USB 存储」——kernel.img 同时包含内核
            本体与内建 initramfs，本实验没有把这两者再分离。
   [不得写] 「已修复」「新镜像可进系统」「前端已启动」——见第五节。
   [不得写] 「6.18.21 版本本身有缺陷」——6.18.21 与 6.18.49 是两条
            不同构建来源的内核树，差异不等于版本号的因果结论。[推断]

三、数据呈现：现象对照

3.1 实验前（20261111 上电，用户口述 + 11-10 同类串口日志）
  "Unable to find LABEL=ROCKNIX, powering off and on should correct it.
   Power off in 3s... 2... 1..."
  11-10 同盘同症状串口：USB 枚举成功（048d:1234 / SN 读到），
  3.536~14.741 s 缺 usb-storage -> scsi host -> sdX 整段，

  LABEL=ROCKNIX: Can't lookup blockdev（×3）。

3.2 实验后（本轮，22:14，用户口述）[实证-板级]
  "按照这个方式替换后，没有报错，开始进入系统初始化界面了"
  即：不再打印 LABEL=ROCKNIX 查找失败，不再 3 s 关机，
  initramfs 已成功以 LABEL=ROCKNIX 挂载 /flash、切入 rootfs、
  进入首启初始化流程。

3.3 由现象可推出的最小事实链 [推断，但证据强度高]
  找得到 LABEL=ROCKNIX  ->  存在 sdX 块设备且 libblkid 能读到卷标
  进入系统初始化        ->  /flash 挂载成功、SYSTEM  squashfs 可用、
                           已切换到用户态 init
  同一块盘、同一套引导字节，只有 kernel.img 不同 -> 差异由 kernel.img 提供

四、原因分析
--------------------------------------------------------------------------------
4.1 为什么可以排除盘侧
  先前「嫌疑一（盘侧，权重高）」的唯一依据是：所有失败都发生在
  CBM2199、所有成功都发生在 Kingston，且失败日志缺 usb-storage ->
  scsi -> sdX 整段。但这两个变量共线，逻辑上不能归因。
  实验 A 把盘固定为 CBM2199，仅换内核即跨过该失败点，直接证伪
  「CBM2199 在这块板子的 Linux 下不绑定 mass storage」。
  盘侧嫌疑由 [推断] 升级为 [已排除]。

4.2 为什么可以认为六特征固化方向正确
  本轮实机使用的是 20261111 CI 产物刷出的 F 盘：cmdline 153 B、
  ramdisk_size=0 内建 initramfs、497 B cfgload / 1466 B aml_autoscript /
  54,984 B dtb.img、卷标 ROCKNIX、无 ceboot，全部由 CI 源码固化而来。
  它们在本轮未被替换，且与 GOLD 盘字节级一致。换内核即能进初始化，
  说明这六项不是故障源，源码级固化 + CI 闸门的方向成立。[实证-板级]
  注意：这同时说明「六特征齐备」是必要条件而非充分条件——
  20261111 原镜像六特征齐备仍失败。CI 闸门目前只校验引导链形态，
  不校验「kernel.img 能否在该板上枚举 USB 存储」，这是闸门的覆盖缺口。

4.3 剩余候选（kernel.img 内部，尚未分离）
  候选一 内核本体差异：6.18.21 与 6.18.49 对 CBM2199 的
    usb-storage / uas 绑定、DWC3 / xHCI / USB PHY / VBUS regulator
    行为不同。仓库 projects/ROCKNIX/packages/linux/package.mk 第 69~71
    行把 S922X|RK3399|RK3566|A311D 固定为 PKG_VERSION="6.18.21"，
    从 kernel.org 拉 vanilla tarball；GOLD 的 6.18.49 来自 ROCKNIX
    官方 20261108 构建的内核树。两者构建来源不同，不只是补丁级别差异。
    [实证-字节 + 推断]
  候选二 内建 initramfs 差异：ramdisk_size=0 表示 initramfs 编进内核
    镜像，随内核一起被 lzop 压缩。两个 kernel.img 的 initramfs
    mount_common() / blkid 查找 / 设备等待逻辑可能不同。
    本机此前尝试离线取明文失败（无 lzop / python-lzo，Docker 镜像
    无 squashfs-tools、容器内 apt 超时、WSL 被安全策略禁止）。
    [未执行]
  候选三 黄金 dtb.img（编译自 6.18.49 内核 DTS）与 6.18.21 内核的
    绑定关系：本轮 DTB 未换，6.18.49 内核用它可启、6.18.21 内核
    用它失败，故 DTB 本身不是独立故障源；但「6.18.21 内核 + 黄金
    DTB」组合的 USB PHY 绑定是否完全匹配，仍未由串口日志确认。[推断]

4.4 本轮仍缺的证据
  [P0] 本轮上电 0~16 s 串口原始日志：确认 6.18.49 + CBM2199 下
       usb-storage detected / scsi host / [sda] Attached SCSI 的时间点，
       与 11-10 失败日志做逐行差分，这是把候选一与候选二分开的关键。
  [P0] 系统初始化完成后的板级状态（见第六节采集清单）。
  [P1] 两个 kernel.img 内建 initramfs 的文件级对比。

五、重要风险提示（必须在交付前说清）
--------------------------------------------------------------------------------
1. 本轮只证明「引导链能走通」，不等于系统可用、前端可用。
   设备仍处于首启初始化阶段，是否跑完、能否 SSH、essway/sway 是否
   拉起，全部 [未执行]。

2. F 盘当前是「6.18.49 内核 + 20261111 SYSTEM（6.18.21 模块）」组合，
   与 GOLD 盘的结构性组合相同，会重现阶段 C 的版本混刷：
   /lib/modules/ 下只有 6.18.21，而 uname -r 为 6.18.49，
   mali_kbase.ko 等外部模块大概率无法加载。
   与 GOLD 的差别是：20261111 SYSTEM 已补
   /etc/profile.d/090-ui_service（UI_SERVICE="sway.service essway.service"）
   且 gpu.driver 默认设为 panfrost，因此前端是否起来不能预判，
   必须实测。不得据本轮结果推断「前端已解决」。[推断]

3. 当前 F 盘是唯一同时具备「CI 六特征 + 能进初始化」的组合，
   建议在继续实验前把它整盘做一次镜像备份（或至少保存
   kernel.img + SYSTEM + 三件套的 md5 清单），避免首启扩容
   改写分区后失去可复现状态。G 盘（Kingston / GOLD）继续保持
   原样，不要擦除，它是唯一完整可进系统的回退盘。

4. 本实验完全可逆：
   python tools/a311d_kernel_bisect.py --restore \
     E:/A311d/AURKNIX-image-A311D-20261031/AURKNIX-image-A311D-20261111/bisect_backup_F_20261111 \
     --dst F --write
   还原后 F 盘回到 6.18.21 原状态（会重现启动失败）。

六、下一步建议（按优先级）
--------------------------------------------------------------------------------
6.1 P0 —— 等设备初始化结束后，立即做板级验收与取证
  串口侧（或 SSH 登录后）：
    dmesg | grep -iE 'usb|scsi|sd |blkid|mali|panfrost'
    findfs LABEL=ROCKNIX; blkid
    uname -r; ls /lib/modules/
    cat /proc/cmdline
    cat /etc/profile.d/090-ui_service
    cat /storage/.config/gpu.driver
    modprobe -n mali_kbase; lsmod | grep -i mali
    systemctl status essway.service sway.service
    ls -l /dev/dri
    systemctl is-system-running
  可复用工具：
    python tools/a311d_usb_boot_probe.py --host <IP> --out <报告.txt>
    python tools/a311d_gpu_stack_check.py --probe-command   # 生成采集脚本
    python tools/a311d_gpu_stack_check.py --live <dump>      # 出报告
  判读要点：
    a) 6.18.49 下 CBM2199 是否完整打印 usb-storage -> scsi -> sdX；
    b) /flash 挂载点、/storage 扩容是否完成；
    c) 模块目录与 uname -r 是否同源，前端服务状态。

6.2 P1 —— 两条修复路线（需用户选一，本轮未改任何构建脚本）
  路线一【对齐参考内核，工程落地最快】
    把 A311D 的 CI 内核对齐到已实机验证的 6.18.49，并保证 KERNEL
    与 SYSTEM 同源，避免版本混刷。可选实现：
      一(a) 把 packages/linux/package.mk 第 69~71 行 A311D 的
            PKG_VERSION 从 6.18.21 提升到 6.18.49（S922X/RK3399/
            RK3566 需评估是否一并改，建议先只给 A311D 分支），
            同步 linux.aarch64.conf 版本头与补丁兼容性，重建后
            KERNEL/SYSTEM 同为 6.18.49。
            前置验证：kernel.org 6.18.49 tarball 可得、Amlogic
            补丁集能应用、CI 可完整构建、闸门通过。
      一(b) 把 GOLD 的 6.18.49 kernel.img 连同配套 6.18.49 模块
            作为固定资产纳入 bootkit。更稳但偏离「CI 源码构建」
            原则，且与已固化的六特征思路冲突，需同步改闸门。
    同时在 tools/a311d_ci_bootchain_check.py 增加一条判据：
      「kernel.img 内核版本 == SYSTEM /lib/modules 目录版本」，
    把阶段 C 的版本混刷变成出图前 FAIL，而不是进系统后才发现。
  路线二【定位 6.18.21 具体缺陷，形态最干净】
    保持 KERNEL/SYSTEM 同源 6.18.21，通过串口差分 + 内建 initramfs
    文件级对比，定位 usb-storage 未绑定的环节再修源码。
    前置工作：需要能用纯 Python 实现 LZO1X 解压从 kernel.img 取出
    vmlinux、再定位 cpio newc 段（本机无 lzop / python-lzo）。
    成本高于路线一，但能保住同源构建，前端风险最低。
  路线三【临时交付】
    以当前 F 盘组合继续验收：若前端能起，可作为临时可用盘交付，
    但必须把「6.18.49 内核 + 6.18.21 模块」登记为已知未闭环项。

6.3 P2 —— 闸门覆盖缺口
  tools/a311d_ci_bootchain_check.py 目前校验六特征字节形态，
  不校验内核能否在该板上枚举 USB 存储。建议在上述路线确定后，
  至少加入「内核版本字符串与 SYSTEM 模块版本一致」及
  「kernel.img 与已验证基线 md5/版本关系」的 WARN 级提示，
  避免再次出现「离线 35 PASS / 0 FAIL、上电仍失败」。
