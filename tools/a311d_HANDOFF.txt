2.1 板级与启动架构
  机型：CAINIAO CNIoT-CORE / LEMO CORE，/proc/device-tree/model 实测为该值
  SoC ：Amlogic A311D（G12B），Cortex-A73/A53，Mali-G52（Bifrost）
  启动：eMMC 内 stock Amlogic U-Boot 2015.01 + aml_autoscript/cfgload 链，
        Android boot image v0（Image.lzo），chain-boot，无 extlinux.conf，
        不向启动介质写 U-Boot firmware。
  分区：sda1 LABEL="ROCKNIX" vfat -> /flash(ro)；
        sda2 LABEL="STORAGE" ext4 -> /storage(rw)；
        sda3 LABEL="GAMES" exfat（首启扩容生成）。
  GPU ：arm,mali-bifrost 节点为 panfrost(Mesa) 与 vendor DDK
        （mali_kbase.ko + libmali）双栈共用，status 缺省即 okay。
        A311D 是 Bifrost，不应启用 arm,mali-midgard 节点。

  为什么用二进制资产而不是 mkimage 重新编译 .src：
    a) U-Boot script payload 前 8 字节是长度前缀（BE32 文本长度 + 4 字节
       0），实测 cfgload 00 00 01 b4、aml_autoscript 00 00 05 72；
       mkimage -T script 不生成该前缀，会破坏老 U-Boot 的 autoscr 解析。
    b) uImage 头含 timestamp / hcrc / dcrc，每次构建都变，实机验证的是
       具体字节。
    c) 黄金 DTB 的 USB VBUS regulator 绑定与本地 DTS 编译产物不同
       （本地产物 74,382 / 80,688 B）。
  已知 WARN（不阻断）：cfgload 的长度前缀 436 与当前文本 425 不一致，
  是 11-09 EDID 等长修正（508 -> 497 B，dsize/dcrc 未重算）遗留；
  Amlogic 2015.01 不校验且实机正常，必须保持原样，不要"修正"。

5.2 已推翻 / 已纠正（防止接手人重复排查）
  1  「20261109 进不了前端是因为没有 libmali 驱动」——早期误判。
     mali_kbase.ko 与 /usr/lib/mali 本就在 SYSTEM 中，真因是版本混刷
     + 默认 GPU 栈回落 libmali + UI_SERVICE 缺失。
  2  「本机实测只能 panfrost 起前端」——用户已明确纠正，与硬件能力
     无关；那只是某次 libmali 切换失败，不是硬件上限。A311D 是
     Bifrost G52，双栈共用节点。
  3  「卷标不一致导致黑屏」——补记六/七的归因已被补记八/九推翻。
     卷标正确是必要条件，不是充分条件；根因在内核阶段看不到 USB
     启动盘的块设备（缺失 usb-storage -> scsi -> sdX 整段）。
  4  「video=HDMI-A-1:D 是损坏字段」——误判。它是 11-09 修 meson DRM
     user-defined mode 黑屏的正确写法，不得改回 1920x1080@60。
     现网 /proc/cmdline 中的 1920x1080@60 来自 U-Boot bootargs，
     与 kernel header 字段来源不同，二者不矛盾。
  5  「6.18.21 把 USB 存储驱动编成模块导致 initramfs 死锁」——已排除。
     外部 ramdisk cpio 66 个条目、0 个 .ko、无 /usr/lib/modules 确实
     属实，但内核配置与现网实测均证明 USB 存储驱动全 =y 内建。
  6  「20261109 可进系统是 CI 构建成果」——不是，是 make_a311d_bootable.py

第七节  接手人最短操作路径
--------------------------------------------------------------------------------

7.1 触发构建
  GitHub Actions -> Build nightly（.github/workflows/build-nightly.yml，
  workflow_dispatch），勾选 A311D（inputs.A311D = true）。
  链路：build-nightly.yml -> build-device.yml -> build-aarch64-image.yml。
  DEVICE=A311D 时闸门 step 自动执行；若六特征不符，构建在发布 artifact
  之前失败，此时应先看闸门日志定位，不要下载镜像刷盘。

7.2 出图后离线复核（本机，刷盘前必做）
  下载 AURKNIX-A311D.aarch64-<日期>.img.gz 及 .sha256，核对 sha256。
    python tools/a311d_ci_bootchain_check.py --repo . --img <路径> --skip-integrity
    python tools/a311d_image_verify.py <路径> --expect-label ROCKNIX
  前者退出码必须为 0；后者结论必须为「可以刷盘」。
  注意：a311d_image_verify.py 用位置参数，传 --help 会被当成文件名。
  可选：对解压后的 .img 去掉 --skip-integrity 做全量 kernel/SYSTEM md5。

7.3 刷盘上电
  建议用盘 C（Kingston，已知能进系统）做 A/B 对照，刷前完整备份。
  首启前清 /storage 残留。串口观察三个关键点：
    a) usb-storage detected -> scsi host -> sdX 是否出现（本次失败正缺这段）
    b) initramfs 是否成功以 LABEL=ROCKNIX 挂 /flash（不应再 poweroff）
    c) /proc/cmdline 尾部是否等于 BOOTIMG_CMDLINE

7.4 前端验收（进系统后）
    uname -r 与 /lib/modules/<ver>/ 是否同源
    modprobe -n mali_kbase / lsmod | grep -i mali
    cat /etc/profile.d/090-ui_service
    cat /storage/.config/gpu.driver
    systemctl status essway.service sway.service
    ls /dev/dri
  可用 tools/a311d_gpu_stack_check.py --probe-command 生成板上采集脚本，
  回传 dump 后用 --live <dump> 出报告。

7.5 失败决策树
  闸门失败            -> 按 FAIL 项修 CI 源码，不要做盘级补丁。
  能进系统、前端不起  -> 查 KERNEL/SYSTEM 同源与 UI_SERVICE/gpu.driver，
                        参考 5.1 第 2 条与 tools/a311d_gpu_stack_check.py。
  仍报 Unable to find LABEL=ROCKNIX
    -> 优先怀疑「6.18.21 内核 + 6.18.49 DTS 编译的黄金 DTB」组合，
       其次考虑回退到 6.18.49 内核同源构建；可用
       tools/a311d_usb_boot_probe.py 在可进系统的机器上做盘 C / 盘 B
       无损对插，区分盘侧与镜像侧。
  回退路径            -> 直接刷 GOLD 20261109-bootsafe-edidmode.img，
                        它可进系统但前端不起，作为安全底。
