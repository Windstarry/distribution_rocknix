  AURKNIX-A311D.aarch64-20261109-bootsafe-edidmode.img，它不是 CI 构建产物，

  产出的镜像字节里、从未固化进构建脚本——这就是「20261109 之后修改的镜像
  一律进不去系统」的回归点，是构建路径切换，不是某一次代码补丁。[实证]

  当前进展：已把阶段 B 的六项引导链特征固化进 A311D 的 CI 构建源码，并加了

2.1 板级与启动架构
  机型：CAINIAO CNIoT-CORE / LEMO CORE，/proc/device-tree/model 实测为该值
  SoC ：Amlogic A311D（G12B），Cortex-A73/A53，Mali-G52（Bifrost）
  启动：eMMC 内 stock Amlogic U-Boot 2015.01 + aml_autoscript/cfgload 链，
        Android boot image v0（Image.lzo），chain-boot，无 extlinux.conf，
        不向启动介质写 U-Boot firmware。
  分区：sda1 LABEL="ROCKNIX" vfat -> /flash(ro)；
        sda2 LABEL="STORAGE" ext4 -> /storage(rw)；
        sda3 LABEL="GAMES" exfat（首启扩容生成）。
  GPU ：arm,mali-bifrost 节点为 panfrost(Mesa) 与 vendor DDK
        （mali_kbase.ko + libmali）双栈共用，status 缺省即 okay。
        A311D 是 Bifrost，不应启用 arm,mali-midgard 节点。

  三方 md5 闭环：本地 GOLD .img == 活机 192.168.31.7 /flash == bootkit。

  为什么用二进制资产而不是 mkimage 重新编译 .src：
    a) U-Boot script payload 前 8 字节是长度前缀（BE32 文本长度 + 4 字节
       0），实测 cfgload 00 00 01 b4、aml_autoscript 00 00 05 72；
       mkimage -T script 不生成该前缀，会破坏老 U-Boot 的 autoscr 解析。
    b) uImage 头含 timestamp / hcrc / dcrc，每次构建都变，实机验证的是
       具体字节。
    c) 黄金 DTB 的 USB VBUS regulator 绑定与本地 DTS 编译产物不同
       （本地产物 74,382 / 80,688 B）。
  已知 WARN（不阻断）：cfgload 的长度前缀 436 与当前文本 425 不一致，
  是 11-09 EDID 等长修正（508 -> 497 B，dsize/dcrc 未重算）遗留；
  Amlogic 2015.01 不校验且实机正常，必须保持原样，不要"修正"。

     进 CI 构建脚本，一重建即全部丢失；阶段 E 的 bootfixed/livefixed
     是盘级补丁，不改变 CI 产物，重建必复发。[实证]
  7  不能简单「保留 20261109 引导链 + 换 20261110 SYSTEM」：前者
     KERNEL 6.18.49、后者 SYSTEM 模块 6.18.21，配对会重现阶段 C 的
     版本混刷，前端依旧起不来。[实证 + 推断]
  8  A311D 与 S922X 的 linux.aarch64.conf 完整 diff 只有 4 行
     （RD_ZSTD / KERNEL_LZO / INPUT_ADC_KEYS / DRM_ETNAVIV），
     USB/SCSI/PHY/INITRAMFS 区段完全一致。[实证]

5.2 已推翻 / 已纠正（防止接手人重复排查）
  1  「20261109 进不了前端是因为没有 libmali 驱动」——早期误判。
     mali_kbase.ko 与 /usr/lib/mali 本就在 SYSTEM 中，真因是版本混刷
     + 默认 GPU 栈回落 libmali + UI_SERVICE 缺失。
  2  「本机实测只能 panfrost 起前端」——用户已明确纠正，与硬件能力
     无关；那只是某次 libmali 切换失败，不是硬件上限。A311D 是
     Bifrost G52，双栈共用节点。
  3  「卷标不一致导致黑屏」——补记六/七的归因已被补记八/九推翻。
     卷标正确是必要条件，不是充分条件；根因在内核阶段看不到 USB
     启动盘的块设备（缺失 usb-storage -> scsi -> sdX 整段）。
  4  「video=HDMI-A-1:D 是损坏字段」——误判。它是 11-09 修 meson DRM
     user-defined mode 黑屏的正确写法，不得改回 1920x1080@60。
     现网 /proc/cmdline 中的 1920x1080@60 来自 U-Boot bootargs，
     与 kernel header 字段来源不同，二者不矛盾。
  5  「6.18.21 把 USB 存储驱动编成模块导致 initramfs 死锁」——已排除。
     外部 ramdisk cpio 66 个条目、0 个 .ko、无 /usr/lib/modules 确实
     属实，但内核配置与现网实测均证明 USB 存储驱动全 =y 内建。
  6  「20261109 可进系统是 CI 构建成果」——不是，是 make_a311d_bootable.py
     重打包产物。
  7  「盘侧嫌疑」——11-11 22:14 实验 A 后【已排除】。同一块
     CBM2199（盘 B / F:）在 6.18.49 kernel.img 下可完成 USB 存储
     绑定、挂 /flash、进入系统初始化。原先「失败都发生在 CBM2199、
     成功都发生在 Kingston」只是内核与盘共线造成的假相关。
     双盘对插验证（实验 C）降为可选，不再阻塞主线。
  8  /etc/os-release 仍写 OS_NAME="ROCKNIX" / 20261031 /
     BUILD_BRANCH=a311d，是 branding 未改，SYSTEM 确实来自
     20261031 AURKNIX CI 构建，勿误判为社区 ROCKNIX rootfs。

第十节  补记：2026-11-11 22:00 上电失败与双盘单变量归因
--------------------------------------------------------------------------------
  本节是截至 2026-11-11 22:20 的最新状态，与前文冲突处以本节为准。
  完整取证与判读见 tools/a311d_boot_disk_diagnosis_20261111.txt。

10.1 发生了什么
  20261111 新构建（六特征全落地、KERNEL/SYSTEM 同为 6.18.21）刷到
  F 盘后上电，仍提示 "Unable to find LABEL=ROCKNIX"，3 s 后自动关机。
  用户补充确认：能进系统的 20261109 GOLD 盘在 G 盘，两盘同时在线。

10.2 本轮新查出的决定性事实
  F 盘 = 048d:1234 VendorCo / CBM2199 / 32 GB（即本文档 2.2 的盘 B）；
  G 盘 = 346d:5678 Kingston DataTraveler / 64 GB（即盘 C）。
  11-10 失败日志的 SerialNumber 7419751033367614176 与 F 盘 PNP 序列号
  逐字相同，确认两次失败都是同一块 CBM2199 盘。
  两盘的 cfgload(497B)、aml_autoscript(1466B)、dtb.img(54984B) md5 三方
  一致；BPB 与根目录卷标同为 ROCKNIX；cmdline 153 B 逐字节相同；
  ramdisk_size 同为 0。F 盘与 20261111 .img 关键文件 md5 全一致，刷盘无误。
  唯一实质差异是 kernel.img（6.18.21 vs 6.18.49，各带内建 initramfs）、
  SYSTEM、FAT 格式参数（F spc=32 / G spc=8）与 G 盘独有附加文件
  （KERNEL 26,822,664 B、kernel2.img 26,826,752 B、KERNEL.md5、
  fs-resize.log）。cfgload 首选 kernel.img，故附加文件不参与本次失败。

10.3 结论口径（必须遵守）
  不能写「6.18.21 内核有问题」，也不能写「CBM2199 盘坏了」。
  两个变量共线：盘 B 只配过 6.18.21（两次失败），盘 C 只配过 6.18.49
  （一次成功）。逻辑上无法分离，需单变量实验。
  「这份镜像可以刷盘」（21:48）仍然成立，它只覆盖离线完整性与六特征，
  不代表板级可启动——本轮正好印证了该分级。

10.4 单变量实验（三选一，均未执行）
  实验 A【最低成本】固定盘 B，只把 G 盘的 6.18.49 kernel.img 换到 F 盘：
    python tools/a311d_kernel_bisect.py --backup <目录> --dst F
    python tools/a311d_kernel_bisect.py --apply --dst F --src G --write
    仍失败 -> 盘侧确证；能进系统 -> 内核侧确证。
    备份已预建：E:/A311d/.../20261111/bisect_backup_F_20261111/，
    还原：--restore <目录> --dst F --write。
  实验 B【快速恢复】先备份 G 盘 FAT 分区文件，再把 20261111 刷到 G 盘
    Kingston 上电；成功则直接达成「6.18.21 同源 + 前端」目标。
  实验 C【证据最干净】用 G 盘启动进系统，把 F 盘插另一 USB 口，
    python3 tools/a311d_usb_boot_probe.py --host <IP> --out <报告>
    看 6.18.49 内核能否让 CBM2199 生成 sdX。
