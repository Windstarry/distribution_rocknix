三、原因分析
--------------------------------------------------------------------------------
3.1 为什么能进系统
  U-Boot 层（三件套 / 卷标 / cmdline / ramdisk_size=0）、DTB 层、
  FAT 层、SYSTEM 层本就无误；唯一缺陷是 6.18.21 kernel.img 在该板上
  不能把 CBM2199 绑定成块设备。换成 6.18.49 kernel.img 后，
  3.636~4.736 s 完成 usb-storage -> scsi -> sda，initramfs 得以
  以 LABEL=ROCKNIX 挂 /flash，系统正常起来。与 11-10 失败日志
  的差分完全自洽。[实证-活体 + 实证-字节]

3.2 为什么前端进程能起、GPU 栈却不健康
  UI_SERVICE 已由 /etc/profile.d/090-ui_service 注入且生效，
  gpu.driver 有效值为 panfrost，所以 autostart 能启动 sway + essway。
  但内核换成 6.18.49 后，模块目录仍是 SYSTEM 打包的 6.18.21，
  /lib/modules/6.18.49 为空，panfrost.ko / mali_kbase.ko 均加载不了，
  DRM 只剩 meson VPU 的 card0，没有 GPU 渲染节点。
  即「服务编排层已通、内核模块层未通」。[实证-活体 + 推断]

3.3 对上一轮推断的修正（必须记录）
  上一轮（22:14）把「6.18.49 内核 + 6.18.21 模块」预判为
  「mali_kbase 加载不了 -> 前端大概率起不来」。本轮实机推翻该预判：
  sway / essway 均 active/running。修正后的正确表述是：
    版本混刷不影响「服务被拉起」，但阻断「GPU 内核模块加载」，
    因此前端能否有画面、是否硬件加速，仍未闭环。
  用户此前「本机实测只能 panfrost 起前端」的纠正也应据此理解：
  这是 libmali 栈在版本混刷下不可用，不是硬件能力上限。
  [实证-活体；前端画面质量为推断]
  22:45 补记：用户目视 HDMI 有画面但非常卡顿，说明版本混刷不阻止
  画面输出，只阻止硬件加速；卡顿归因见第七节与卡顿归因报告。

四、建议方案（按新证据重排优先级）
--------------------------------------------------------------------------------
路线一【推荐：同源 6.18.49 构建，一次性解决引导 + GPU 栈】
  目标：KERNEL 与 SYSTEM 同为 6.18.49，让 /lib/modules/6.18.49
        有完整 modules.dep，panfrost.ko / mali_kbase.ko 可加载，
        /dev/dri 出现 renderD128，前端从「进程 running」升级为
        「硬件加速可用」。
  实现（22:45 已做前置核实，不是「改一行」）：
        1) projects/ROCKNIX/packages/linux/package.mk 第 68~71 行
           的 6.18.21 由 S922X|RK3399|RK3566|A311D 四设备共用，
           必须拆出 A311D 单独 case 并置 6.18.49，严禁全局替换；
        2) 同步 devices/A311D/linux/linux.aarch64.conf 版本头并按
           6.18.49 跑 oldconfig，保留 CONFIG_DRM_PANFROST=m；
        3) packages/linux/patches/mainline/ 的 5 个补丁做 dry-run；
        4) 完整重建后验收 modules.dep / panfrost / renderD128。
  已核实：kernel.org v6.x/linux-6.18.49.tar.xz HTTP 200、
        154,627,808 B（2026-09-02），源码可得；
        运行内核 /proc/config.gz 已含 CONFIG_DRM_PANFROST=m。
  仍 [未执行]：补丁适配、defconfig 差异、CI 实跑、板级复验。
  本轮证据支持度：6.18.49 内核已在同一块盘、同一套 DTB、
        同一套引导链上实机验证可启动，风险显著低于继续用 6.18.21。

路线二【形态最干净，但成本高】
  保持同源 6.18.21，通过串口差分 + 内建 initramfs 文件级对比
  定位 usb-storage 未绑定环节后修源码。修完可保留 CI 6.18.21
  同源构建，模块与内核天然匹配。需补齐 LZO1X 解压能力。

路线三【临时交付 / 现状登记】
  以当前 F 盘组合作为可运行临时盘：系统可用、sway + essway running。
  但必须登记三项已知未闭环：
    a) 6.18.49 内核 + 6.18.21 模块，GPU 内核模块未加载、无 render node；
    b) /flash/kernel.img.md5 记录与 kernel.img 不一致；
    c) is-system-running = degraded（6 个 tmp-*.mount failed）。
  不建议作为最终交付镜像发布。

配套改造（无论选哪条路线都建议做）
  1) tools/a311d_ci_bootchain_check.py 增加判据
     「kernel.img 内核版本 == SYSTEM /lib/modules 目录版本」，
     把版本混刷变成出图前 FAIL；现有闸门只校验六特征字节形态，
     不校验内核与模块版本一致性，也不校验板级 USB 存储兼容性。
  2) 修 /flash/kernel.img.md5 同步逻辑，避免 OTA 校验踩坑。
  3) 保留 G 盘（Kingston / GOLD）为唯一完整回退盘，不擦除；
