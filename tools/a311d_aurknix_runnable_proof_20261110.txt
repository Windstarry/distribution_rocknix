【结论】

  AURKNIX 在该板上可运行，且已运行到「多用户 + 网络 + 三分区挂载 +
  SSH 登录」的完整 Linux 系统层，不存在架构性移植障碍。当前状态是
  「系统可运行、前端未启动」，不是「系统起不来」。

  前端阻断有唯一实锤：运行内核 6.18.49，而 SYSTEM 内的内核模块目录
  只有 6.18.21，modprobe mali_kbase 报
  "FATAL: Module mali_kbase not found in directory /lib/modules/6.18.49"。
  叠加 UI_SERVICE 未赋值、gpu.driver 未设定，essway/sway 均 inactive(dead)。

  由此得到本轮最关键的工程推论：把阶段 B 引导链固化进 CI 产物，同时
  让 KERNEL 与 SYSTEM 同源（同为 6.18.21），既保留「能进系统」，又消除
  版本混刷，使前端具备启动条件。这条路径已被本次活体数据双向支持。

三、原因分析
--------------------------------------------------------------------------------

  3.1 为什么「AURKNIX 可运行」成立
    - rootfs 来自 20261031 AURKNIX CI 构建的 SYSTEM（/etc/release =
      A311D.aarch64-20261031，BUILD_BRANCH=a311d），在本板上完成了
      initramfs 挂载、squashfs root、overlay、systemd、网络、SSH。
    - 三分区布局、首启扩容、exFAT GAMES 均按 AURKNIX 逻辑完成。
    - 用户态 Mali 栈齐全：/usr/lib/libmali.so.1.9.0、
      libmali-meson-r51p0-wayland-gbm.so、libMaliVulkan.so、
      /usr/lib/mali/*、/usr/lib/modprobe.d/mali-gpu-noauto.conf，
      以及 firmware/arm/mali/* 全在。
    => 移植缺的不是包、不是驱动、不是 rootfs，而是 KERNEL 与 SYSTEM
       同源 + 少量启动配置。

  3.2 为什么前端没起来（实锤，非推断）
    - 运行内核                  : 6.18.49
    - /usr/lib/kernel-overlays/base/lib/modules/ : 仅 6.18.21
      （含 mali-bifrost/mali_kbase.ko）
    - /lib/modules/6.18.49/     : 空
    - modprobe -n mali_kbase    :
        FATAL: Module mali_kbase not found in directory /lib/modules/6.18.49
    - /etc/profile.d/090-ui_service : 不存在
    - grep UI_SERVICE 仅有 001-functions:193 的引用与 999-export:56 的
      导出声明，无任何赋值
    - /storage/.config/gpu.driver : 空
    - essway.service / sway.service : 均 inactive (dead)、disabled
    - systemctl is-system-running  : degraded
    - systemctl --failed 7 项：tmp-assets/cores/database/joypads/
      overlays/shaders.mount 与 rocknix-report-stats.service，
      属资产挂载与统计上报，不是 GPU 根因。
    => 与本仓 11-10 00:24 的判断一致：版本混刷 + 配置缺口，
       「缺 libmali」是 11-09 23:48 之前的早期误判，已被证伪。

  3.3 本轮对上一轮结论的两处修正
    a) 盘侧嫌疑降权（原补记九 4.1 列为高权重）：本次成功启动的是
       普通 USB2.0 U 盘走 usb-storage，与失败日志里 048d:1234
       CBM2199 属同类路径，却在 6.18.49 下完整生成 sdX。
       同一条枚举链在 20261110 的 6.18.21 内核下整段缺失，
       差异更可能来自内核/DTB/启动链组合，而不是「盘太特殊」。
       注意：三块盘 VID 各不相同，不能据此断言盘完全无关，
       仍建议保留双盘对插验证作为最终确认手段。
    b) 「USB 驱动被编成模块」彻底排除：活体 /proc/config.gz 显示
       USB_STORAGE / UAS / SCSI / BLK_DEV_SD / XHCI / DWC3 全 =y，
       且内核用内建 initramfs，不依赖 SYSTEM 里的 .ko。

--------------------------------------------------------------------------------
四、对「把阶段 B 引导链固化进 CI 产物」的推论
--------------------------------------------------------------------------------

  逐条给出活体依据，说明六项特征为何必须同时保留：

  1) cmdline 完整
     活机 /proc/cmdline 尾部与黄金 cfgload 的 bootargs 逐字一致，
     boot=LABEL=ROCKNIX / disk=LABEL=STORAGE 由它提供。
     20261110 CI 的 kernel header cmdline 全空，且 cfgload 依赖
     ceboot 二次注入，链条更长更脆。CI 产物应让 header cmdline
     与 cfgload bootargs 同源且一致，U-Boot 无论「追加」还是
     「替换」结果都相同。

  2) ramdisk_size=0 / 内建 initramfs
     活机 CONFIG_INITRAMFS_SOURCE 指向内建 initramfs，
     kernel.img Android v0 头 ramdisk_size=0，USB 驱动全内建，
     内核阶段即可枚举启动盘。20261110 CI 用 7,346,176 B 外部
     ramdisk（cpio 内 0 个 .ko、无 /usr/lib/modules），
     与实机验证形态不符。

  3) 经典 cfgload / aml_autoscript
     活机 /flash 为 497 B cfgload（bootargs 硬编码、固定
     dtb.img、bootm 三段式）+ 1466 B aml_autoscript
     （sddtb/usbdtb + autoscr，无 ceboot、无 cfgload_env）。
     CI 现为 3012 B Generic_cfgload + 3078 B cfgload_env(ceboot)
     + 1382 B aml_autoscript，属另一套设计。

  4) 实机 54,984 B dtb.img
     活机 /flash/dtb.img md5 0fee9ffd...，与本地 GOLD 及新提取的
     bootkit 完全一致；其 Bifrost GPU 节点默认 okay、
     USB regulator 为 regulator-usb-pwr / regulator-usb-switch。
     CI 自编 80,688 B DTB 的 USB VBUS regulator 属性不同，
     是本轮 USB 块设备缺失的主要板级嫌疑。

  5) 卷标 ROCKNIX
     活机 sda1 LABEL="ROCKNIX"，/proc/cmdline boot=LABEL=ROCKNIX，
     /flash 以 ro 挂载成功。设备级 options 已在 11-10 20:46 提交
     a57bc4ba2b 覆盖为 ROCKNIX（20261110 镜像构建于 07:34/15:34，
     早于该提交，故产物仍是 AURKNIX）；该项已固化，重建即生效。

  6) 不引入 ceboot
     活机 /flash 无 cfgload_env、无 config.ini，aml_autoscript
     不含 ceboot。CI 的 u-boot/package.mk 会生成
     Generic_cfgload_env 并写入镜像，须从构建链移除。

  综合：CI 产物的目标形态 = 同源 6.18.21 KERNEL+SYSTEM +
  上述六项阶段 B 引导链特征。这既让「能进系统」可复现，
  又消除 3.2 的模块版本错配，是唯一同时满足两个目标的方向。

五、事实更正与未验证项（必须如实标注）
--------------------------------------------------------------------------------

  5.1 启动盘身份更正
      本次上线盘是 346d:5678 Kingston DataTraveler 3.2（62.9 GB），
      既不是 152d:0583 JMS583 NVMe 盒，也不是 048d:1234 CBM2199。
      这是本项目记录的第三块盘。请确认是否更换过 U 盘；
      这会改变「两块盘固定对照」的前提，但不影响第二、四节的
      可运行性与归因结论（所有结论均基于本次活体机本身）。

  5.2 品牌字符串
      /etc/os-release 为 OS_NAME="ROCKNIX"、OS_VERSION="20261031"、
      BUILD_ID=a3758508...、BUILD_BRANCH="a311d"、HW_DEVICE="A311D"。
      SYSTEM 确实来自 20261031 AURKNIX CI 构建，但 branding 未改。
      排查时勿据 OS_NAME 误判为社区 ROCKNIX rootfs。

  5.3 未验证项
      - 本轮为只读取证，未做任何板级改动、未刷盘、未重启。
      - 「CI 同源 6.18.21 内核 + 黄金 DTB」这一组合尚未构建、
        尚未上电验证；黄金 DTB 编译自 6.18.49 内核 DTS，
        与 6.18.21 内核的绑定关系属推断，须由 CI 实跑 + 上电确认。
      - 前端能否在同源构建后启动，须在刷入新 CI 镜像后单独验收；
        本轮只能证明当前阻断原因，不能证明修复后一定成功。
