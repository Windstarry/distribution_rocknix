0. 一句话结论

   AURKNIX 在 A311D 上「能进系统」的最后一个镜像是
   AURKNIX-A311D.aarch64-20261109-bootsafe-edidmode.img。
   它不是 CI 构建产物，而是用 tools/make_a311d_bootable.py 在
   ROCKNIX-S922X-BOX.aarch64-20261108.img 的已验证引导链上重打包出来的。
   2026-11-10 为修前端/GPU 栈改为 GitHub Actions 完整重建后，
   CI 产物把 10-31 就存在的启动链缺陷（空 cmdline + 外部 ramdisk +
   自编 DTB + 卷标 AURKNIX）原样带了回来，而 bootsafe 的修复只落在
   重打包工具里、从未固化进构建脚本。因此「20261109 之后修改的镜像
   一律无法进入系统」——回归点是构建路径切换，不是某一次代码补丁。

9. 回归点与根治方向

   9.1 分界线：20261109-bootsafe-edidmode.img（11-09 晚间重打包）
       -> 20261110.img（11-10 CI 完整重建，07:34 / 15:34）。
       用户所述「之后修改的镜像无法进入系统」与实测引导链完全吻合。

   9.2 不能简单「保留 20261109 引导链 + 换 20261110 SYSTEM」：
       20261109 的 KERNEL 是 6.18.49（来自 ROCKNIX 参考镜像），
       而 AURKNIX 的 SYSTEM 模块是 6.18.21，两者配对会重现
       阶段 C 的 KERNEL/SYSTEM 混刷，前端依旧起不来。
       要同时修好「能进系统」与「能进前端」，KERNEL 与 SYSTEM
       必须同源（同为 6.18.21 或同为 6.18.49）。

   9.3 因此根治方向只有一条：把阶段 B 的引导链特征固化进 A311D
       的 CI 构建产物，而不是每次刷盘后打补丁：
         kernel header cmdline 完整（boot=LABEL=ROCKNIX ...
           video=HDMI-A-1:D）
         ramdisk_size=0，回到内核内建 initramfs
         cfgload / aml_autoscript 用经典 CoreELEC 简版
         dtb.img 使用实机验证的 54,984 B（GPU/USB/EDID 图齐全）
         BPB 卷标与 DISTRO_BOOTLABEL 统一为 ROCKNIX
         不引入 ceboot / cfgload_env 新链，device_trees 与
         dtb.img 保持单一来源
       这样 CI 重建后 KERNEL(6.18.21) 与 SYSTEM(6.18.21) 同源，
       GPU 栈修复才可能真正生效。

   9.4 短期验证（不依赖重建）：在 192.168.31.7 的 ROCKNIX 系统上
       把 CBM2199/AURKNIX 盘插到另一个 USB 口（无损、无需换启动盘），
       运行 tools/a311d_usb_boot_probe.py，判定良好内核能否生成 sdb、
       blkid 是否有 LABEL="ROCKNIX"，据此区分盘侧与 AURKNIX 侧问题。
       或刷 20261109-bootsafe-edidmode.img 到该盘，先固定
       「这块盘能否启动」这一变量。
       待澄清：20261109 当时「可进系统」是在 JMS583 盘还是
       CBM2199 盘上验证的。
