一、结论摘要
--------------------------------------------------------------------------------
1. 用户反馈「HDMI 画面有输出，但非常卡顿」属实，并补齐了上一轮
   [未执行] 的 HDMI 目视验收项：画面存在，性能不达标。[实证-用户目视]

2. 卡顿由两个叠加因素构成，均有活体证据：
   a) 输出被固定在 3840x2160@60Hz、scale 1.0，单帧 829 万像素；[实证]
   b) 系统没有可用的 GPU 渲染节点，合成/绘制由 CPU 承担。[实证 + 推断]

3. 没有 GPU 渲染节点的原因是版本混刷：运行内核 6.18.49，
   而 panfrost.ko / mali_kbase.ko 只存在于 6.18.21 模块目录，
   /lib/modules/6.18.49 为空、modprobe 失败。[实证]

4. 因此本轮状态口径为：
   「引导层已通、服务层已通、渲染层未通」。
   禁止表述：「已修复」「移植完成」「GPU 栈正常」「前端完全可用」
             「panfrost 已工作」「卡顿根因已定位到某个具体函数」。

三、原因分析
--------------------------------------------------------------------------------
3.1 因果链 [实证 + 推断]
  实验 A 为了让系统能起来，把 kernel.img 换成实机验证过的 6.18.49，
  但 SYSTEM 仍是 20261111 CI 产物，其模块树是 6.18.21
    -> /lib/modules/6.18.49 为空、panfrost.ko 加载不了
    -> DRM 只剩 meson VPU 的 card0，没有 renderD128
    -> sway 只能把 /dev/dri/card0 当 dumb/软件合成设备；
       ES 的 libEGL DRI2 硬件路径初始化失败
    -> 3840x2160@60Hz、scale 1.0 的 829 万像素/帧由 CPU 绘制
    -> ES 单核 96.6% 持续满载，sway 21.6%
    -> 用户目视「有画面但非常卡顿」

3.2 直接因素与根本因素的区分
  直接因素：4K 分辨率 + CPU 合成。降分辨率可显著减少填充量，
            但只是缓解，不产生 GPU 加速。[推断，未实测]
  根本因素：KERNEL 6.18.49 与 SYSTEM 模块 6.18.21 版本混刷。
            这一点同时解释了上一轮 gpu_stack_check 的 4 项 FAIL
            （版本不一致 / modules.dep 缺失 / 无 GPU 模块 /
            无 render node）。[实证]

3.3 与上一轮推断的关系（修正而非推翻）
  上一轮写「sway 37.4% CPU 且无 GPU 渲染节点，疑似软件渲染，
  HDMI 画面待目视」。本轮用户目视「有画面但非常卡顿」，
  加上 4K 模式、libpixman/Mesa EGL 映射、ES EGL 失败日志、
  单核 96.6% CPU，使「软件渲染导致卡顿」的推断获得强支撑，
  但 wlroots 具体后端仍未由日志确认，仍标注 [推断]。
  同时确认：版本混刷不阻止画面输出，只阻止硬件加速。

3.4 不得越级的结论
  - 不得写「卡顿根因已定位到 panfrost 驱动缺失」：还包含 4K 分辨率
    这一独立放大因素，两者权重未做单变量对照。
  - 不得写「同源 6.18.49 构建一定能解决卡顿」：未构建、未实测。
  - 不得写「切换 libmali 就能解决」：libmali / mali_kbase 同样是
    6.18.21 模块，当前同样不可加载。[实证-模块路径]

四、建议方案
--------------------------------------------------------------------------------
4.1 P0 立即可做的可逆缓解（不重建、不改盘、不落盘）
  在设备上执行（或由我在 SSH 恢复后代为执行并采集前后 CPU）：
    export SWAYSOCK=/run/0-runtime-dir/sway-ipc.0.sock
    swaymsg output HDMI-A-1 mode 1920x1080@60Hz
  回退：
    swaymsg output HDMI-A-1 mode 3840x2160@60Hz
  若需持久化，在 /storage/.config/sway/config 追加一行：
    output HDMI-A-1 mode 1920x1080@60Hz
  说明：
    a) 1920x1080 在 EDID modes 列表中确实存在，像素量降为 1/4；[实证]
    b) 当前 config 未固定 mode，运行时改动重启即失效，风险可控；[实证]
    c) 不建议用 scale 2 提速——合成缓冲仍是 4K，不减少填充量；[推断]
    d) 该实验同时可分离「分辨率」与「无 GPU 加速」两个变量的权重，
       是本轮唯一还缺的单变量对照。[建议，未执行]

4.2 P0 根因修复：同源 6.18.49 构建（路线一，已做前置核实）
  目标：KERNEL 与 SYSTEM 同为 6.18.49，/lib/modules/6.18.49 有完整
        modules.dep，panfrost.ko 可加载，/dev/dri 出现 renderD128，
        使 sway/ES 走硬件 GLES；同时保留已实机验证的引导链。
  改动清单（不是「改一行」）：
    1) projects/ROCKNIX/packages/linux/package.mk 第 68~71 行：
       把共用 case 拆成两段——
         S922X|RK3399|RK3566) 维持 6.18.21
         A311D)                PKG_VERSION="6.18.49"，PKG_URL 沿用
                               kernel.org v6.x 模板
       严禁把 6.18.21 全局替换掉。
    2) projects/ROCKNIX/devices/A311D/linux/linux.aarch64.conf：
       同步版本头注释，按 6.18.49 跑 oldconfig/savedefconfig 复核新增项，
       必须保留 CONFIG_DRM_PANFROST=m 与 CONFIG_DRM_MESON=y。
    3) packages/linux/patches/mainline/ 5 个补丁对 6.18.49 做
       patch --dry-run，冲突项单独适配。
    4) 完整重建后验收：uname -r == /lib/modules 目录名、
       modules.dep 存在、lsmod 有 panfrost、/dev/dri/renderD128 出现、
       sway/ES 渲染库含 panfrost 路径、目视流畅度。
    5) 同源达成后再单独验证用户原始诉求的 libmali / mali_kbase
       vendor 栈；本轮路线一只保证 panfrost 开源栈可用，
       不能把两者混为一谈。
  前置核实结果：kernel.org 6.18.49 tarball HTTP 200 可得；
        6.18.49 内核已在本板、本盘、本 DTB、本引导链实机启动；
        运行内核 /proc/config.gz 已含 CONFIG_DRM_PANFROST=m。
  剩余风险：补丁跨小版本适配、6.18.49 defconfig 差异、
        CI 仍需实跑；均 [未执行]。

4.3 其他路线（保留，不因本轮证据升级）
  路线二：保持同源 6.18.21，串口差分 + 内建 initramfs 文件级对比，
          定位 CBM2199 上 usb-storage 未绑定环节后修源码。
          形态最干净，但需 LZO1X 解压能力，成本最高。
  路线三：以当前 F 盘组合临时交付，必须登记版本混刷、
          kernel.img.md5 不一致、degraded 6 个 tmp-*.mount；
          若叠加 4.1 的 1080p 持久化可作为临时可用方案。
          不建议作为最终镜像发布。

4.4 配套改造（无论选哪条路线）
  1) tools/a311d_ci_bootchain_check.py 增加判据
     「kernel.img 内核版本 == SYSTEM /lib/modules 目录版本」，
     把版本混刷变成出图前 FAIL；现有闸门只校验六特征字节形态，
     不校验版本一致性，也不校验板级 USB 存储兼容性。
  2) 补一条「出图后渲染层 WARN」：/dev/dri 是否含 render node、
     sway 是否映射硬件 DRI 驱动（需活机采集，CI 只能做静态提示）。
  3) 修 /flash/kernel.img.md5 同步逻辑，避免 OTA 踩坑。
  4) 保留 G 盘（Kingston / GOLD）为唯一完整回退盘，不擦除；
     F 盘当前状态先整盘镜像备份后再继续实验。
